## 1. 무엇을 정하려던 대화였나

"내가 하는 작업들(GAS 자동화, 파이썬 파이프라인, 앱인토스 등)을 기록할 블로그를 어디에 만들까"에서 출발해서,
플랫폼 선택 → 참고 사례 조사 → 디자인 시안 → 개발 방법론 전환까지 이어진 논의.

## 2. 플랫폼 결정

### 네이버 vs 워드프레스 vs 자체 제작

| | 장점 | 단점 |
|---|---|---|
| 네이버 블로그 | 초기 유입 빠름, 이웃 기능 | 계정이 내 소유 아님, 저품질 리스크, 개발·자동화 검색은 구글에서 일어남 |
| 워드프레스 | 글쓰기 편함, 플러그인 | 호스팅비, 보안·업데이트 관리, 느림 |
| 자체 제작(정적) | 비용 거의 0, 빠름, 완전한 소유 | 발행 과정에 손이 감 |

### 결론: 자체 제작(정적 사이트)

**"자체 제작은 SEO에 불리하다"는 오해였음.**
구글은 무엇으로 만들었는지 보지 않고 콘텐츠 품질·속도·사이트맵·메타태그를 본다.
워드프레스가 유리하다는 말의 실체는 "플러그인이 그걸 자동으로 챙겨준다"는 것뿐이고,
자체 제작 시 처음 한 번 제대로 넣으면 끝난다. 오히려 정적 사이트가 속도에서 유리.

**추가 근거**
- 이미 정적 사이트 구조(GitHub Pages/Vercel) 경험이 있어 학습 비용 0
- 비용은 도메인비 연 2만원 수준
- 발행 과정이 불편하면 그것조차 자동화할 수 있는 상황

## 3. 참고 사례 조사

### 3-1. Simon Willison (simonwillison.net + til.simonwillison.net) — 핵심 참고

- 사이트를 둘로 분리: 본 블로그(긴 글) / TIL 사이트(짧은 메모)
- 1년에 43개 주제, 148개 TIL 발행
- 글감 공식: **"방금 배운 것"에 대한 TIL + "방금 만든 것"에 대한 글**

**왜 그렇게 러프하게 올리는가 (별도 논의)**
1. 독자용이 아니라 6개월 뒤의 나를 위한 검색용 메모
2. 다듬는 비용을 없애야 지속된다 (한 편 10분 → 1년 148개)
3. 러프한 좁은 제목이 실제 검색어와 일치해 유입에 유리
4. 삽질 과정이 남아 있어 "실제로 해본 사람" 신뢰 신호
5. 도메인 분리 자체가 "여기는 대충 써도 되는 곳"이라는 심리 장치

**단, 문장은 대충 써도 구조는 일정하게 지킨다.**

### 3-2. 디지털 가든형

- **Andy Matuschak** (notes.andymatuschak.org) — 노트끼리 링크, 백링크 표시. "시간순 나열은 글을 일회용으로 만든다"
- **Maggie Appleton** — 글마다 성숙도 표시(rough/growing/stable). 미완성 글도 올릴 수 있게 하는 장치

### 3-3. 한 칸 (hankan.app) — 국내 사례, 최종 참고 모델

- 구조: **채운 칸(만든 것) / 작업 일지 / 작업실(소개)** 세 구역, 한 페이지
- 일지 항목이 한 줄짜리도 있음 → 발행 부담 최소화
- "빈 칸" 자리를 만들어 프로젝트가 적은 걸 컨셉으로 전환
- 컨셉 단어(칸)가 이름부터 각 구역 제목까지 일관
- **딱딱하지 않은 이유는 디자인이 아니라 짧은 존댓말 문장** → 국내 감성은 말투로 만들 수 있다

> 참고: 이 사이트에 광고는 없음. HTML에 있던 건 애드센스 소유 확인용 메타태그였음.

## 4. 디자인 시안

`work-log-example.html` 제작. Simon 구조 + Maggie의 성숙도 표시 + 시트 모티프.

- 위: 만든 것(프로젝트 카드) / 아래: 배운 것(행 번호 있는 표 형태 목록)
- 상태 열: 러프 / 다듬는 중 / 정리됨
- 구글 시트를 재료로 삼은 디자인(수식 입력줄, 행 번호, 셀 형광펜 hover)
- 메모 제목은 좁고 구체적으로 (예: "GAS 6분 실행 제한에 걸릴 때 트리거로 이어 돌리기")

**결정 사항**
- 매출·수익 지표는 공개하지 않음
- 국내 감성 문제 → 구조는 유지하고 말투로 온도를 올리는 방향

## 5. 확정된 사양

| 항목 | 결정 |
|---|---|
| 첫 버전 범위 | 한 페이지로 완결, 나중에 확장 |
| 발행 방식 | 클로드코드에서 바로 작성·발행 |
| 애드센스 | 글 쌓인 뒤 나중에 (1차에서 제외) |
| 배포 | GitHub Pages |
| 글 형식 | 마크다운 파일만, HTML 직접 안 건드림 |

**발행 방식을 클로드코드 직접으로 정한 이유**
작업 기록 대부분이 "방금 클로드코드로 만들다 막혔고 이렇게 풀었다"라서,
그 자리에서 "방금 거 일지로 남겨줘" 한 마디로 끝나는 게 마찰이 가장 적다.
옵시디언은 사이트에 안 올릴 개인 메모용으로 계속 사용.
텔레그램 자동 발행은 사이트가 자리 잡은 뒤 2차 프로젝트.

## 6. 방법론 전환 — SDD → ECC

### 두 방식의 차이

| | SDD (스펙 주도) | ECC |
|---|---|---|
| 비유 | 도면을 먼저 완성 | 실력 있는 시공팀에 맡김 |
| 누가 생각하나 | 내가 미리 (SPEC.md) | 클로드코드가 (계획서) |
| 내 역할 | 스펙 작성 + 게이트 검수 | 계획 승인 + 눈으로 확인 |
| 교환 조건 | 통제를 사고 시간을 냄 | 시간을 사고 통제를 냄 |

### 적용 기준 — 프로젝트 시작 시 세 질문

1. **틀리면 금전 손해가 나는가?**
2. **결과를 눈으로 확인할 수 없는 로직인가?**
3. **운영 중인 시스템을 건드리는가?**

→ 하나라도 해당하면 **"안 만들 것 목록 + 눈으로 확인 가능한 완료 기준" 한 장**을 추가.
→ 전부 해당 없으면 요청문만으로 ECC 진행.
→ 정산·배분·송금 관련은 **항상** 해당.

### 프로젝트별 분류

- **안전장치 필요**: USDT 정산 워크플로우, 원데이님 납품 정산, 기존 GAS 배분 시스템 수정
- **ECC 그대로**: 작업 기록 사이트, 앱인토스 미니앱 화면, 핫딜 애그리게이터, 독서클럽 사이트
- **중간(외부 계정 영향)**: 네이버 블로그 자동화 → ECC로 만들되 "초안 저장까지만, 발행은 수동" 안전장치

### ECC로 가도 유지할 두 가지

1. **안 만들 것 목록** — AI가 기능을 부풀리는 걸 막음
2. **눈으로 확인하는 완료 기준** — "다 됐습니다"를 맹신하지 않게 함

> SDD 전면 적용은 중단. 클로드 앱 기억에 반영 완료.
> 클로드코드 쪽 CLAUDE.md에도 같은 규칙을 별도로 넣어야 함.
> 프로필 사용자 선호에 남은 기존 SDD 지침 정리 필요. (미완료)
